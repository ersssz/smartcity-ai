# Native Arrival + durable WalkSession: integration design

2026-10-20. Read-only design against `2be738f1c815b746334dfb9125148d897cbfc85b` and the current working tree. **Proposed implementation, no native/migration/device changes performed.** Covers [T05](../plan/tasks/t05-durable-walk-session.md), [T07](../plan/tasks/t07-gps-arrival.md), US-15–18/23; normative rules: [SPEC](../plan/PRODUCT-SPEC.md#сессия-и-gps-прибытие), [ARCH §4](../plan/ARCHITECTURE.md#4-walksession-offline-gps-и-звук), [DECISIONS](../plan/DECISIONS.md). Root owns schema/contract approval and integration. No provider, account, external dependency or paid operation is needed for this design.

The existing Kotlin `WalkSession.kt` is a **process-local acquisition permit**, not the durable story session. Preserve its generation cancellation, one-use 10-second Start permit, main-looper control and `START_NOT_STICKY`. Name the new store distinctly (`SessionStore`, not another ambiguous `WalkSession`). Existing manual-only `EditorialWalk` is not a canonical WalkBundle: use an explicit adapter with labeled provenance; do not relabel old progress as server/GPS evidence.

## Recommended ownership: one SQLite file, separate projections

Use the existing `astanaai-walks.db` for atomic journal/projection/outbox updates. Native writes Arrival-related projections; JS writes story commands through the repository. Both use a common versioned control row. This avoids a full Kotlin port of the story reducer and avoids claiming atomicity across a native database and an Expo database. An Arrival does not change story cursor/answers, so its transaction need not execute the JS reducer.

The installed `expo-sqlite/android/.../SQLiteModule.kt:defaultDatabaseDirectory` resolves to `context.filesDir/SQLite`. Root must explicitly configure and verify both connections against that exact canonical file, including a same-file cross-connection transaction test. Do **not** use `context.getDatabasePath()` by assumption or accept an arbitrary path from bridge input. Native opens an existing migrated database read-write; it cannot silently create/migrate a second one. Both connections enable foreign keys, compatible WAL and bounded busy handling; no dependency on newer SQLite JSON/RETURNING functions. Framework SQLite + Expo's SQLite interoperability is a device integration gate, not proven by Node tests. If it fails, move all writes behind a native store Adapter; do not split the atomic aggregate over two files.

Root-owned v2 migration introduces these logical tables (names proposed):

| Table | Invariant / writer |
|---|---|
| `session_control(session_id, bundle_hash, bundle_revision, phase, version, current_flag, updated_at)` | Prepared/active/paused/completed/abandoned; one current session and at most one active session via constraints. Shared CAS row. Durable `active` is **not** permission to restart tracking. |
| `session_story(session_id, story_json)` + immutable bundle storage | JS reducer's cursor/manual marks/quest answers; no second authoritative `phase` field. Snapshot combines this row with control. Bundle may contain agreed origin/end and public geometry; event rows may not. |
| `session_events(session_id, event_id, sequence, kind, stop_id?, canonical_poi_id?, quest_id?, proof?, occurred_at)` | Unique `(session_id,event_id)`; bounded typed fields only. No raw JSON request/fix, lat/lon, accuracy history, provider extras or free text. UTC time describes an observation; sequence orders commits. |
| `session_arrivals(session_id, canonical_poi_id, anchor_id, event_id)` | Unique `(session_id,canonical_poi_id)` for the selected bundle's eligible places; contains no user's position. Native only. |
| `local_discoveries(canonical_poi_id, award_kind, event_id, earned_at)` + manual/quest award projections | Global unique `(canonical_poi_id,first_app_confirmed_nearby)`, separately unique `(session_id,quest_id,award_kind)` for quests. `manual_reported`, `quest_completed`, `gps_nearby` stay distinguishable. |
| `notification_outbox(event_id, notification_id, locale, template_id, state)` | First-discovery intent is created in the same transaction, stable notification identity. No coordinates, tokens or exact timestamps in notification/public copy. |

All mutations use `BEGIN`/bounded busy handling, re-read current row, validate phase/bundle/current stop, CAS `version`, append event, update affected projection and outbox, then commit. Affected Session snapshot is the consistent SQL view of these projections, **not** an independently overwritten JSON cache. Publish UI state only after commit. Conflict reloads and reports/rebases the command; it never blindly retries a stale whole snapshot. Re-delivery of the same event returns its recorded result; a reused ID with different command content fails. An in-app toast is derived from durable unseen events, not treated as the award itself.

Stable POI aliases come from validated public bundle/evidence metadata before acquisition starts; normalize to canonical IDs before unique checks. Do not generate an identity from coordinates or title. Unknown/ambiguous aliases cannot earn an automatic first discovery. A later alias merge must preserve/merge existing first-discovery keys transactionally rather than minting a second award.

## Interface and native Implementation

Keep the public WalkSession Interface `open`, `dispatch`, `snapshot`; hide the following native Adapter calls in `mobileRepository.ts` / the module wrapper:

```ts
open(sessionIdOrValidatedBundle): Promise<SessionSnapshot>
dispatch({ eventId, expectedVersion, command }): Promise<SessionSnapshot>
snapshot(): Promise<SessionSnapshot>
// Private acquisition Adapter, not arbitrary anchor coordinates from UI:
startTracking({ sessionId, expectedBundleHash, expectedRevision }): Promise<NativeWalkState>
stopTracking({ reason: 'pause' | 'manual_only' | 'complete' | 'abandon' }): Promise<StopResult>
// onProgressChanged: {sessionId, version}; never a Location/event payload queue.
```

JS repository executes pure story transitions against fresh control; native `SessionStore.kt` reads/verifies the selected persisted bundle/descriptor and implements Arrival/control/outbox transactions. New `ArrivalDetector.kt` owns the rolling filter; `ArrivalPolicy.kt` owns validated pilot constants; `DiscoveryNotifier.kt` consumes durable intents. These are private Implementation files, not extra public app-level Modules. Start binds `(sessionId,bundleHash,revision,processGeneration)` and only the visible Activity may request it. Never persist a restartable permission/permit or recreate one from a session row. Revision adoption, pause/resume and changing eligible stop reset the detector.

Arrival eligibility is the single currently selected observation anchor. Compare it with neighboring eligible anchors/known aliases in the validated descriptor: if one fix cannot uniquely distinguish different POIs, wait for a unique position; never award every POI in a 60 m circle or choose an arbitrary nearest tie. A later explicitly selected stop can be evaluated after a reset. This conservative pilot rule can miss close sites; it cannot be presented as field-calibrated recognition.

## Exact detector policy and RAM lifetime

Each `LocationManager` callback runs native regardless of screen/AppState. First check process generation/service identity, active control lease and selected immutable revision. Run these rules before any bridge signal:

1. Finite valid coordinates, available finite nonnegative reported accuracy **<=30 m**, age `0 <= nowElapsedNanos-fix.elapsedRealtimeNanos <=15 s`. Use `elapsedRealtimeNanos`, not wall-clock time. Reject duplicate/nonincreasing observation timestamps across GPS/network callbacks; duplicates/out-of-order delivery cannot increase samples/dwell. A rejected stale duplicate cannot extend an existing window.
2. Keep at most the previous accepted raw fix in RAM, **logical TTL <=15 s**, plus the foreground map point with the same TTL. Candidate state contains only anchor/POI ID, first/last monotonic time and count. No raw-point queue, SQLite fix table, pending bridge locations, crash/log attachment or persistent elapsed-time window. Check elapsed expiry on every access and schedule cleanup even if no subsequent fix arrives; Stop/revision/permission loss clears immediately. A suspended CPU can delay that cleanup callback: logical expiry is not a promise of byte-zeroing RAM at exactly 15 s. Backgrounding removes the UI point but does not discard the native candidate.
3. Reject movement speed `distance(previous,current)/deltaElapsed >3 m/s` (and a valid reported speed >3 m/s). Invalid time or implausible jump cannot start/advance dwell. Clear the candidate on jump, poor accuracy, outside radius, ambiguity, provider/permission interruption or a gap **>15 s**; wait for a new plausible window. Keep the prior good raw reference only until its TTL. An isolated outlier never becomes a new arrival seed.
4. Start/continue a candidate only when distance to the eligible outdoor anchor **<=60 m** and uniquely attributable. Arrival requires **>=30 s of monotonic span and >=3 distinct plausible samples**, with every accepted gap <=15 s. Three fast points are insufficient; a 30-second sleep with no delivered points is insufficient. These are initial calibration parameters, not spoof resistance or proof of entering a venue.
5. Produce a coordinate-free intent with deterministic/idempotent event identity for that session/POI. In one native SQL transaction verify current session/revision/active phase, insert Arrival, conditionally insert global first discovery, event/projection and outbox. Rollback produces no confirmed UI success/notification. A repeat in another session may have an Arrival record but cannot create another first discovery.

Android documents `Location.elapsedRealtimeNanos()` and `SystemClock.elapsedRealtimeNanos()` as comparable, monotonic within a boot including sleep; they do not order observations across reboot. Reset all rolling state on process start/reboot and use database event sequence for durable ordering. Human timestamps remain device observations and can move backwards. [Location reference](https://developer.android.com/reference/android/location/Location#getElapsedRealtimeNanos()), [SystemClock reference](https://developer.android.com/reference/android/os/SystemClock#elapsedRealtimeNanos()).

## Stop, restoration and notification denial

| Trigger | Immediate native action | Durable result / UI |
|---|---|---|
| Explicit Start/resume, visible app | Validate selected bundle/schema and current session; consume one-use permit; start location FGS | Commit active command, then bind tracking only after Start succeeds. Failed tracking leaves a clear manual/degraded state, never claims GPS running. No notification grant required for manual Start. |
| Lock/background | Keep existing explicitly started FGS; no service recreation; clear foreground point/audio behavior follows Audio Adapter | Detector/journal continue natively while callbacks actually arrive. Wake/foreground calls snapshot; absence of callbacks is a gap, not inferred presence. |
| Pause / notification Stop | **First** revoke process generation, clear detector/raw point, remove location listener/health callbacks and stop FGS/audio; no SQLite/network/JS wait before cancellation | Native store appends pause and bumps control version. Receiver uses bounded `goAsync()` completion, no JS dependency. Snapshot reconciles on next read. Ordinary notification Stop means pause; explicit “finish early” is abandoned, not completion. |
| GPS off / permission loss / FGS failure | Same immediate cancellation; expose typed degradation | Persist interruption/pause if possible. Manual restart/progress remains available. Re-enable requires explicit visible resume, fresh permit and empty dwell; no backlog Arrival. Notification permission loss alone is **not** location permission loss. |
| End/abandon | Cancel acquisition first | Persist the validated complete/abandon command and distinct terminal state. Do not first persist generic pause and then attempt an active-only completion; use one reason-aware command. Turning GPS off to continue manually leaves the story active. |
| Process death, force-stop, task removal or reboot | No persisted runnable location job/boot receiver/sticky restart | On first open, if no current process lease exists, transactionally normalize saved active to paused/interrupted; retain committed achievements/cursor. Never infer that `onDestroy` ran. A surviving valid same-process lease is reconciled, not cancelled by every React remount. |

**Stop/SQL race:** detection acceptance occurs on the serialized native control looper. After generation revocation no new fix/intent is accepted. Queued, unstarted old-generation intents are dropped. An already accepted in-flight transaction may finish a pre-Stop achievement; do not erase it or describe it as post-Stop tracking. SQL pause follows as a barrier; Stop's durable-success result waits for that barrier, while actual acquisition cancellation is immediate. No new Start/resume until it settles. The shared version CAS prevents an in-flight cached JS command from resurrecting active phase. If DB is locked/full/corrupt, report `trackingStopped + pausePending/storageError`; never claim durable pause succeeded. A new process still restores paused. On listener removal failure preserve the existing `STOP_CLEANUP_FAILED` error rather than claiming no acquisition.

**US18:** keep achievement persistence independent of notification delivery. Android 13+ does not require `POST_NOTIFICATIONS` to launch an FGS, but an FGS notification must still be supplied. With permission denied, its notice can appear in Task Manager instead of the notification drawer. Show an in-app active-tracking/Stop control and explain this limitation; do not promise a visible drawer button. Keep achievements readable without GPS, notification permission or a network call. [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission).

Use separate ongoing-service and first-discovery notification channels. For each committed first discovery create one outbox intent. If achievement notifications are denied/channel-blocked, persist `suppressed`; never replay it when permission is later granted. For allowed delivery, use stable tag/ID and `setOnlyAlertOnce`. **SQLite and NotificationManager cannot share a transaction:** choose durable `pending -> attempted` before the OS call, replay only never-attempted intents, and expose a crash between claim/post as an undelivered notification with a still-present in-app achievement. This favors no repeated first alert over guaranteed OS delivery. ARCH's “replay undelivered” needs this distinction recorded by Root; do not claim exactly-once external delivery from stable IDs alone. On Android post failure record failure, never roll back/re-award the discovery.

Start only from a visible Activity with allowed location/provider and declared `location` FGS permissions/type; preserve blocked `ACCESS_BACKGROUND_LOCATION`/boot restart rather than widening permissions. Android 12+ restricts background FGS starts and Android 14+ checks while-in-use prerequisites. Continuing an existing user-started FGS is distinct from creating a new one in background; device behavior remains a measured gate. [Foreground start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), [location FGS requirements](https://developer.android.com/develop/background-work/services/fgs/service-types#location).

## Migration and implementation order

1. **Root: shared contract/migration first.** Define Session v2 typed command/event/control schemas, bundle identity adapter and proof enum. One transaction validates/imports v1 `walk_current`, history and manual discoveries; map ready→prepared and saved active→paused. Preserve cursor/answers/manual provenance; import existing collection as manual story completion, never GPS. Write an idempotent import marker only after validation; failure keeps original rows readable. Do not drop diagnostics SQLite/counter, user settings or old rows before successful verification. An unsupported/corrupt source yields safe recovery, not a new empty successful profile. Bundle version and DB version are independent.
2. **T05: durable repository.** Replace cached overwrite with event IDs/version CAS and consistent snapshots; add abandoned, replay results, unique quest/collection awards and restoration. Tests through `open/dispatch/snapshot` on actual SQLite, including v1 fixtures and write failures. Read validated public anchor descriptors from selected revision; manual-only mode remains usable before GPS work.
3. **T07: private native detector + store.** Implement policy and actual native SQLite Arrival/discovery/outbox transaction. Integrate controller before UI visibility gate; notification Stop writes paused control. Root independently checks same-file Expo/native writes, listener-generation cancellation and cross-writer CAS. Remove production coupling to `startDiagnostic()`; do not weaken old diagnostic tests merely to pass production behavior.
4. **US18 + UI reconciliation.** Decouple optional notification permission, expose native progress invalidation/snapshot refresh and proof-specific labels. Update `model.ts`/`engine.ts` eligibility to allow a genuine Arrival **or** manual mark to unlock reading/quest interaction, while retaining provenance. GPS never auto-completes a quest. Stop/audio/revision/error states reconcile from committed state.
5. **Device acceptance separately.** Signed standalone build/upgrade and the matrix below. An implemented replay detector is not field acceptance, and screen-off survival alone does not prove a screen-off Arrival was committed.

## Required evidence before calling this complete

- Deterministic policy tests through its Interface: 60/30/15/3 boundaries, 29.999 vs 30 s, two vs three samples, duplicate providers/out-of-order/future timestamps, speed/jump, >15 s gap, close anchors/aliases, poor accuracy, revision/current-stop reset. Recorded replay is visibly labeled; it cannot populate real GPS proof silently.
- Actual SQLite public-interface tests: event/quest/first-POI uniqueness across sessions and canonical aliases; transaction rollback/disk-full; v1 import twice; active restore paused; native pause vs concurrent stale JS answer/resume/complete; unchanged origin/bundle revision; no coordinates in journal/outbox/discovery/public export and no raw live fixes in SQLite/WAL. Agreed bundle origin/end/public geometry remain distinguishable from forbidden raw fix history. Test both independent connections against the same file. Public payload allowlist is still separately enforced by PublicCollection.
- Crash injection around event insert/projection/outbox/commit/UI and notification attempt/post: exactly one achievement/result, clear best-effort notification outcome, no resurrected tracking. Notification denied before Start and revoked while active both retain in-app/manual achievements; granting later creates no old alert burst.
- Physical Android: actual outdoor detection while screen off with JS suspended, then foreground snapshot; Stop in notification with Activity closed; Start/permission revocation/provider loss; process kill/reboot/task removal/force-stop recovery; fresh explicit resume. At least the T01 30-minute test with >=20 minutes locked, anonymized callback gaps/accuracy/rejection counts and measured battery; Android 14+ plus second-device matrix remains separate from the current API31 Xiaomi.
- Privacy inspection covers SQLite main/WAL/SHM, backup/extraction exclusions, logs/crash output, bridge queues and deletion. Record IDs/counts/relative intervals and proof types for diagnostics, **no raw coordinates**. Schema inspection is necessary but does not prove coordinates were never retained by another path. No device/settings inspection was performed for this document.
