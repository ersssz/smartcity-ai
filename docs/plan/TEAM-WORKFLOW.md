# AstanaAI — протокол двух Codex и приёмки

Дата: 20 октября 2026. Статус: окончательный план исполнения, а не выполненные задачи. Пользователь делегировал оставшиеся плановые решения Root; дополнительное согласование разбивки не требуется. Текущая фаза заканчивается планом: репозиторий, приложение и внешние issues этим документом не создаются.

## Роли и самостоятельность

Root — координатор, владелец архитектурной целостности и интеграции. Друг — самостоятельный владелец Implementation своих законченных модулей. Реализация имеет полноценную важность: ошибки данных, состояния и UI напрямую определяют качество продукта. Люди предоставляют реальные устройства/аккаунты, выполняют требующие физического присутствия полевые/языковые проверки и оценивают пользу.

| Зона | Владелец решения | Порядок |
|---|---|---|
| Цель, приоритет и критерии приёмки | Root в рамках делегированных решений пользователя | Фиксирует в спецификации; согласованные функции сохраняются |
| Общие Interface, WalkBundle v1, миграции | Root; можно явно передать одну задачу другому | Один владелец конкретного изменения |
| Native foundation, зависимости, lockfile, build config | Изначально Root | Друг подаёт краткое предложение; после baseline владение отдельной задачей можно передать |
| CityEvidence, WalkPlanner, backend | Изначально Root | Друг вправе владеть ограниченными задачами данных/расширения |
| WalkSession, Android, offline, audio | Друг после foundation | Implementation и локальное исправление выбирает самостоятельно |
| Merge и интеграционный gate | Root | По конкретному SHA и доказательствам, без микросогласования каждого шага |
| Независимая проверка | Другой исполнитель/ограниченные субагенты | Проверяет результат, а не доверяет слову «готово» |

Root пишет наиболее неопределённые вертикальные части и не превращается в диспетчера каждой функции. Друг может менять внутреннее устройство своего модуля без ожидания Root, если сохраняет Interface, scope и критерии. Изменение общего контракта, миграции, платного обязательства или обещания пользователю требует решения владельца; новая платёжная обязанность не принимается автоматически.

## Источник правды и обмен между ноутбуками

После отдельного старта разработки — один удалённый Git-репозиторий, по независимому clone на каждом ноутбуке. Общая папка по сети не используется. Интегрированное состояние находится в main, задача — в ветке codex/<ticket>-<slug> от указанного commit SHA. Номер билета, Base SHA и версия Interface записываются перед стартом; SHA сейчас не выдумывается.

Общий контекст хранится в репозитории: короткие инструкции агента, продуктовая спецификация, глоссарий, важные архитектурные решения, контракты и актуальная задача. Чаты не считаются автоматически общими. Одинаковые skills сами по себе не доказывают одинаковые модели, настройки, лимиты или доступность инструментов.

Windows-MCP нужен для настройки и отдельных наблюдений; он не является транспортом кода и непрерывным диспетчером второго Codex. Root учитывает ControlStatus и не борется с человеком за управление. Секреты остаются в разрешённых локальных/серверных хранилищах; их не копируют в handoff, Git, screenshots и PR.

Навыки Matt Pocock на обоих ноутбуках закреплены commit 5beb35b040e3de97e54fa9e386d7e42d15c295c2. При начале задачи агент читает только подходящие skills и контекст: to-tickets для зависимости/вертикального результата, codebase-design для Interface, implement/TDD для реализации, code-review для двух осей, writing-for-agents для краткой передачи. Настройочные hooks и чужие shell-примеры не исполняются автоматически.

## Цикл задачи

1. Root выбирает билет, чьи реальные блокировки закрыты принятыми SHA. У каждого Codex исходно одна активная задача. Готовность человека/аккаунта/устройства проверяется до назначения зависимого теста.
2. В пакет входят: ID, Base SHA, ветка, версия контракта, цель, scope, блокировки, AC, ошибки, доказательства и разрешённая самостоятельность. У каждого билета есть точная привязка к US/AT спецификации; при изменении поведения обновляются нормативный источник и относящиеся проверки.
3. Исполнитель читает текущую спецификацию и нормативные решения, воспроизводит baseline, реализует законченный путь. Поведенческие проверки пишутся на согласованном Interface; CI/команды берутся из среды проекта, а не дублируются в длинном AGENTS.
4. Исполнитель регулярно запускает относящиеся проверки и типы; полный набор — в конце задачи. Самостоятельно исправляет проблемы внутри scope и проводит self-review.
5. Возвращает review-ready: SHA, результаты команд, demo, фактические ограничения и известные дефекты. Список планов и наличие кода не засчитываются как результат.
6. Root фиксирует base/head SHA и непустой diff; независимые Standards и Spec review выполняются отдельно. Используются спецификация и стандарты репозитория; отсутствие стандарта не превращает вкусовое замечание в обязательное нарушение.
7. После исправлений проверяются новый SHA и затронутые сценарии. Root интегрирует green-изменение и запускает относящийся интеграционный путь. Для значимого Android-поведения нужна сборка/устройство.
8. Билет accepted только после проверки AC и доказательств. Человек/агент не закрывает другие родительские задачи по косвенному успеху.

Статусы: ready-for-agent → claimed → in-progress → review-ready → accepted; blocked содержит точную причину и зависимость. Все текущие критерии не выполнены: ready означает «можно начинать при запуске фазы разработки», а не «пользователь уже поручил сейчас кодить». Механический Base SHA выдаётся при старте и не является отдельной продуктовой блокировкой.

Если исполнитель упёрся, он возвращает конкретное противоречие, рекомендуемый вариант и последствия. Независимую работу продолжает. Root отвечает на изменение Interface и продуктового обещания, не утверждает каждую внутреннюю функцию. Блокировки обновляются по факту, а не по календарю.

## Параллельный старт без конфликтов

T01 (Root) и T02 (Друг) независимы. Затем T03 фиксирует общий WalkBundle v1 и native foundation. После этого T04 (реальный запрос → предложение → preview, Root) и T05 (fixture → сессия → восстановление → итог, Друг) идут параллельно. Fixture явно обозначен. Их интеграция происходит по одному Interface без ожидания готовности всей системы. Общие schema/migrations/lockfile меняются только назначенным владельцем.

Перед каждым параллельным циклом Root проверяет пересечение модулей, общих файлов и зависимостей. При необходимом изменении контракта сначала интегрируется совместимое расширение, затем отдельные потребители, затем удаление старого варианта. Большой механический refactor не маскируется под независимые пользовательские функции.

## Gates, сроки и правила выпуска

Оценки — инженерные ориентиры без ожидания доступа/полевых людей, не гарантированные даты. Более 50 часов в неделю не превращаются в 50 часов непрерывной полезной работы: учитываются проверки, обмен контекстом и исправления.

| Gate | Ориентир | Проверяемый результат |
|---|---|---|
| G0 | Первые 3–5 дней | Native, screen-off GPS, 3 языка аудио, offline-права/карта, foot-routing, данные и ресурс при $0 доказаны либо описан конкретный FAIL |
| G1 | Первый целый путь примерно 2–3 недели | Реальные POI → план → прохождение → offline/resume → итог на устройстве. Пока обязательные функции не приняты, это внутренняя проверка пути |
| G2 / M2-TECH | Закрытая исследовательская бета ориентировочно 3–5 недель | Все обязательные возможности и нормативный контентный минимум, три глубокие зоны; T18 принят. До поля нет обещания проверенного сопровождения |
| G3–G4 / FIELD-PASS | В пределах 1–3 месяцев при доступных ресурсах | Пилот и реальное поле, углубление повторной ценности, эксплуатационная проверка и материалы трека; FIELD-PASS обязателен перед внешним T22 |

Gate FAIL меняет прогноз и выбранный Adapter. Он не разрешает молча убрать три языка, квесты или коллекции. Технический путь может начинаться с одной зоны; первая полная бета выполняет нормативный минимум M2 PRODUCT-SPEC по EXPO, Байтереку и старому центру. Базовый автоматический городской каталог и три зоны глубокого guided-содержания различаются. Отчёт покрытия не выдаётся за одинаковое качество прогулок по всему городу.

GPS Arrival в бете означает нахождение рядом с наружным anchor. Это не вход в музей. ManualVisitMark хранится отдельно; призов и лидербордов нет. Offline включает сохранённый пакет карты/материалов/заранее доступного аудио/прогресса. Offline-перестроение пешеходного графа не обещается. Онлайн-коррекция перехода к тому же плану может быть автоматической в нормативных пределах; смена остановок/темы/существенное удлинение требует согласия пользователя.

До M2-TECH отдельно закрывается live-routing gate T02: выбранный Adapter законно строит реальную пешеходную геометрию от текущего GPS-старта и к согласованному концу, включая фактический возврат. Ограничение провайдера публичными anchors не разрешает скрытно менять старт/конец. Явный выбор другого anchor меняет WalkRequest и показан пользователю; несчитанный подход не рисуется прямой линией или вымышленным connector. Без законного решения beta-gate остаётся закрытым, независимая работа продолжается.

## Definition of Done

Для каждого билета:

- Все его AC имеют фактическое доказательство; пропущенное явно названо и не считается PASS.
- Зафиксированы Base/HEAD SHA, версии контрактов/данных/контента, результаты относящихся проверок и среда.
- Успешно воспроизводится пользовательский результат и указанные ошибки; fixture/симуляция/поле различимы.
- Нет новых скрытых секретов, платежей, утечек точного GPS и нелицензированных assets.
- Есть независимые результаты Standards и Spec; блокирующие замечания устранены или билет не принят.
- Проверен интегрированный результат; для состояния/навигации/фоновой работы доказан реальный Android, а не только компиляция.
- Изменённые инструкции/контракты актуальны; handoff содержит только нужный контекст.

Блокирующие дефекты для беты: потеря подтверждённого прогресса, ложное утверждение GPS/входа, заведомо неверный критический путь/расписание, утечка данных/управления профилем, непреднамеренный платный вызов, отсутствие обещанного offline/языкового минимума. Косметические дефекты допускаются только перечисленными и без нарушения критического пути.

Полевую и компетентную языковую проверку нельзя имитировать агентным согласием. Если поле недоступно, техническая работа продолжается и допускается только маркированная закрытая исследовательская бета 18+ после M2-TECH; FIELD-PASS остаётся закрытым до реальных прогулок T19 и обязателен перед внешним T22. Недоступная обязательная языковая/функциональная проверка не становится PASS. Root не объявляет внешний продукт готовым по одному видео или самоотчёту исполнителя.

## Сдача результата задачи

Handoff: ID; Base SHA → HEAD SHA; контрактная revision; что работает с точки зрения пользователя; фактически выполненные команды/устройства; ссылки на обезличенные доказательства; ошибки/ограничения; что блокирует следующую задачу. Секретные значения и точные личные треки отсутствуют.

После нескольких задач оценивать время ожидания Root, долю возвратов, дефекты после интеграции и время до принятого результата. Увеличивать параллельность только при независимых scope и работающей приёмке. Строки кода и число агентов не являются мерой готовности продукта.
