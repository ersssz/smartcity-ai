# Own-app Android UI instrumentation

Interface: `am instrument -w -e scenario sequence -e actions <fixed-ID CSV> kz.astanaai.diagnostics.test/kz.astanaai.diagnostics.test.OwnUiInstrumentation`.

This separate, debug-signed test APK targets only `kz.astanaai.diagnostics`. It uses public Android Instrumentation / UiAutomation / AccessibilityNodeInfo methods, never React hooks, shell input, settings changes, permission grants, or another application's controls. It has no application permissions, Activities, services, or network adapter.

Every instrumentation run launches only the own MainActivity and waits for the opening; `am instrument` may restart the target process, so an unpersisted UI is not preserved between calls. Scenarios: `launch` (launch/record only), `inspect` (bounded tree), `capture` (known location-free city/canonical screen required), `sequence` (execute up to 30 approved action IDs), `smoke` (leave city introduction if present, open canonical walk preview, preserve existing session). `inspect`/`capture` also work as action IDs inside a sequence, where they inspect that step's current screen.

Startup emits fixed live phase/elapsed status before and after unlock checks, automation connection/configuration, test storage, own Activity launch/admission, opening and first recording. Launch uses the public target Context with an explicit own MainActivity Intent, then a 20-second own-root admission loop. A null root may be awaited; any observed foreign package, lock or foreign window is refused. It no longer uses `startActivitySync` or an idle wait: the [Android Instrumentation reference](https://developer.android.com/reference/android/app/Instrumentation#startActivitySync(android.content.Intent)) documents that the synchronous call waits for application idle. This removes that unbounded wait without relaxing authorization. Other Android framework calls themselves may still exceed the scenario deadline; phase status distinguishes these failures.

Actual `work/android-ui-smoke-own-0.4.0.log` confirmed the asynchronous start returned at 60 ms, followed by an immediate foreground refusal before a first action. Root independently observed the launcher during process recreation. `work/android-ui-smoke-settle-0.4.0.log` then confirmed the 500 ms attempt still refused at 555 ms, one poll and zero actions. The final bounded attempt uses a fixed 2500 ms settling interval with lock/deadline checks at most 100 ms apart, then reads window identity/flags only. During admission, a null root or an **inactive and unfocused** `com.miui.home` TYPE_APPLICATION / `com.android.systemui` TYPE_SYSTEM window may be awaited within the 20-second limit. Active/focused foreign windows, permission dialogs, unknown packages/types and locked state still refuse immediately. No tree, screenshot or action occurs until the unchanged own-window guards admit the target. Up to five fixed waiting checkpoints report elapsed milliseconds/poll count. First-root/refusal metadata exposes only `OWN`/`KNOWN_LAUNCHER`/`SYSTEMUI`/`UNKNOWN`, without labels or private package names. This is startup waiting, never foreign-window authorization. No further relaxation is proposed; the actual focused APK device attempt belongs to Root.

Exception: diagnostic `scenario policy` performs only fixed synthetic string checks and a caught regex flag probe; it does not connect UiAutomation, open MainActivity, read UI, capture screens, inspect lock state, or alter permissions/settings. `am instrument` itself can still restart the target process. Its status reports `PATTERN_FLAG_0X100_SUPPORTED`/`UNSUPPORTED` and, when the portable policy initializes and exact Unicode matching passes, `POLICY_COMPATIBILITY_PASS`. Generic failures report only a fixed phase and at most four exception class names, never messages/stacks/UI data.

Diagnostic `scenario windows` launches only the own MainActivity, then records at most 32 window metadata entries: numeric type, active/focused flags, pixel bounds and root availability. Package/title are exposed only for the target application and `com.android.systemui`; everything else is `OTHER`. It reads no tree labels, takes no screenshots, performs no clicks or scrolling, and changes no settings. The result separately records the compiled guard outcome (`unchanged_guard`, retained for diagnostic compatibility) and elapsed stage durations. The 180-second deadline is never reset; Android framework calls themselves can exceed it.

Every click matches normalized **exact** visible text or content description, then clicks that node or its own-package clickable ancestor. Normalization only collapses whitespace. A missing offscreen action may scroll the single visible own-package vertical ScrollView, at most 8 times. No coordinate clicks, injected keys, global actions, arbitrary labels, external Intents, or permission-dialog handling exist. A locked screen, foreign window, ambiguous action, or denied standard instrumentation stops execution. A passive bar exception requires **all** of: exact package `com.android.systemui`, TYPE_SYSTEM, inactive and unfocused, full width of the own active/focused TYPE_APPLICATION window with origin (0,0), height at most 8%, and exact top/bottom edge. Top title must be empty/`StatusBar`; bottom title must be `NavigationBar`/`NavigationBar0`/`Панель навигации`. A title alone never exempts a window. NotificationShade, IME, active/focused windows, interior/large/narrow overlays, unknown packages/roots and other titles are refused. A system dialog requires `USER_ACTION_REQUIRED`; the tool never dismisses it.

Approved IDs and exact localized labels live in `src/kz/astanaai/diagnostics/test/UiPolicy.java`. Initial IDs: `city_exit`, `canonical_entry`, `choose_walk`, `expand_card`, `preview_walk`, `consent_public_start`, `start_walk`, `listen_chapter`, `pause_audio`, `stop_audio`, `locale_ru`, `locale_kk`, `locale_en`, `mark_manual`, `pause_walk`, `resume_walk`, `stop_walk`, `scroll_forward`, `scroll_backward`, `scroll_top`, `inspect`, `capture`, `wait_short`, `wait_audio`. `scroll_top` moves the single own vertical ScrollView backward at most 8 times / 20 seconds, rechecking own windows on every step. Reaching the boundary is success; exhausting the limit without proving the boundary is an error. Quest answer inputs are intentionally absent until independently approved visible choices are added in source.

`resume_walk_footer` is a separate fixed action for the repeated Resume controls. It accepts only the same exact RU/KK/EN Resume label and an own, enabled, visible accessibility `android.widget.Button` with ACTION_CLICK. The target's complete positive-area bounds must lie inside the active/focused own application window and within its bottom 20% (including the exact 80% boundary). Body controls above that boundary and partially offscreen targets are excluded; multiple qualifying targets refuse with `AMBIGUOUS_ACTION_RESUME_WALK_FOOTER`. The window geometry and target class/clickability are checked again after refresh immediately before the public accessibility action. This action never scrolls content to find its fixed footer. Other action matching, guards and capture rules are unchanged; geometry is used only for selection, never coordinate input.

Focused-discovery IDs: `discovery_all`, `discovery_history`, `discovery_architecture`, `discovery_weather`, `weather_sun`, `weather_rain`, `weather_cold`, `weather_windy`, `place_saken`, `place_bayterek`, `place_detail`, `discovery_back`, `guided_walk`, `read_story`. All use exact fixed locale labels except two narrowly bounded own-control descriptions: weather uses the fixed localized `Weather and events:` prefix (maximum 240 characters), and the two places permit their exact known localized title plus `. ` and public editorial text (maximum 600 characters). No caller-supplied prefix/text exists. `place_detail` is restricted to known Saken/Baiterek detail labels. The legacy `smoke` scenario still expects the previous canonical-entry flow; use a fixed sequence for the new discovery home. For example, inspect history/Saken, return, set rain, collapse context, select Architecture/Baiterek:

```text
discovery_history,place_saken,capture,discovery_back,discovery_weather,weather_rain,capture,discovery_weather,discovery_architecture,place_bayterek,capture
```

Actual startup states, loading and label changes may require different approved sequences. Unsupported external-map/source actions are deliberately absent: tests must stay in the own application.

`confirm_end` activates only an own, visible, enabled clickable control bearing one of the nine exact canonical ending labels. For return-to-start, the RU/KK/EN labels are `Я у старта · завершить`, `Бастауға жеттім · аяқтау`, and `At the start · finish`. For a last-stop ending they are `Завершить у последней остановки`, `Соңғы аялдамада аяқтау`, and `Finish at the last stop`. For a chosen finish they are `Я у финиша · завершить`, `Мәреге жеттім · аяқтау`, and `At the finish · complete`. These labels come from `apps/mobile/src/canonical/presentation.ts`; no label, prefix, endpoint, coordinate or completion payload can be supplied by the caller. The normal own-window, exact-label, ambiguity, enabled-state and action bounds remain unchanged. A missing ending fails normally instead of resetting or advancing a session. This is a manual end confirmation for a business-flow test, never proof of physical/GPS arrival or field passage. No GPS, permission, capture or foreign-window authorization is added.

After each action, a bounded, redacted own-package label tree and, when the safe screen is proven, a screenshot are saved in a fresh `run-*` directory under `getTargetContext().getExternalFilesDir("android-ui-tests")`, normally `/sdcard/Android/data/kz.astanaai.diagnostics/files/android-ui-tests/`. Instrumentation runs under the target UID; it does not attempt to write another package's external folder or inspect/change existing user data. The exact evidence path is returned in status bundles. Canonical screenshots require the canonical saved-walk breadcrumb or manual-mode status; city screens use known city-map labels. Raw-coordinate-like labels suppress capture and are redacted from the tree. Intro/legacy/unknown screens produce a documented capture skip, not a claim of visual evidence. Dumps contain no node bounds, device IDs, input field values, arbitrary error messages, or other-package labels.

The focused discovery capture policy uses a composite, locale-consistent signature: the exact Home header plus at least one of the five fixed public place names, or a fixed place title plus the exact Why section and Show-on-map CTA. Fully fixed public map-marker descriptions are also recognized as place identity. A place title alone (including in a legacy collection), a generic Why heading, unknown places, a missing map CTA, coordinate-like text or visible input cannot prove a new discovery screen. The earlier standalone discovery-map/Why labels no longer grant capture. The accumulator stores only bounded boolean evidence, not UI strings. Each dump records `screen_policy=PUBLIC_DISCOVERY_COMPOSITE`, `LEGACY_FIXED_LABEL` or `NOT_PROVEN`; unchanged own-window guards still run before and after a screenshot.

Build with the installed SDK/JDK only:

```powershell
& tools/android-ui/build.ps1
```

The build uses javac, D8, aapt2, zipalign and apksigner without Gradle or downloads, signs with the app's existing **public Android debug key**, verifies the APK and emits its absolute path/hash. It writes only `work/android-ui-build/` outside the Git checkout. The pure-Java policy self-test is part of this build; it is not device evidence.

Example invocation for the integrator (not run by the builder):

```powershell
adb install -r '<absolute path printed by build>'
adb shell am instrument -w -e scenario smoke kz.astanaai.diagnostics.test/kz.astanaai.diagnostics.test.OwnUiInstrumentation
adb shell am instrument -w -e scenario sequence -e actions 'city_exit,choose_walk,expand_card,preview_walk,consent_public_start,start_walk,scroll_top,listen_chapter,wait_audio,pause_audio,stop_audio,locale_kk,locale_en,locale_ru,scroll_top,mark_manual,stop_walk' kz.astanaai.diagnostics.test/kz.astanaai.diagnostics.test.OwnUiInstrumentation
```

The example sequence assumes the legacy walk is still prepared: leaving the city opens the canonical preview directly. With an existing legacy session, insert `canonical_entry` after `city_exit`; use the smoke report to choose the actual path. Sequences require their stated starting UI; missing/changed/disabled labels fail rather than reset, abandon, or erase progress. `wait_short` is 400 ms and `wait_audio` is 4 seconds; every wait rechecks foreground/lock state. Each lookup is bounded to 20 seconds, the entire scenario to 180 seconds (except an Android framework call that itself fails to return). A successful ACTION_CLICK proves only that Android accepted the accessibility action. Screen/state assertions, audible playback, offline behavior, restart restoration and field/GPS acceptance remain separate checks. OEM refusal is reported; this tool makes no claim of bypassing Xiaomi's input restrictions.
